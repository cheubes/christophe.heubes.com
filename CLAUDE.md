# christophe.heubes.com

Personal site of Christophe Heubès: a profile page (professional career) and the "Thought Figures" series of illustrations ("Figures de pensée" in French: intellectual concepts, cognitive laws and biases). Static, bilingual (French / English) site, generated with Jekyll and hosted on GitHub Pages.

## Project status

`specs/` is the source of truth for every design decision: before writing or modifying code, read the spec files relevant to the task.

## Structure of `specs/`

- **`functional-specifications.md`**: site scope, target users, user journeys, cross-cutting rules (bilingualism, navigation), out of scope.
- **`data-model.md`**: the Illustration entity, its attributes, the generation pipeline (concept → SVG → page), naming conventions and validation constraints.
- **`technical-specifications.md`**: tech stack, hosting/deployment, architecture (rendering, Jekyll collections, routing), performance, accessibility, SEO.
- **`style-guide.md`**: visual identity (colors, typography, spacing), base UI components (sidebar, hamburger, tiles, footer...), iconography.
- **`screens/`**: one functional specification per screen (goal, content, interactions, states, responsive):
  - `home.md`: profile page
  - `gallery.md`: Thought Figures gallery
  - `technical-drawing.md`: Thought Figure detail

## When and how to use these specs

- **Before any implementation**, read the file(s) relevant to the task. The four cross-cutting specs (`functional-specifications.md`, `data-model.md`, `technical-specifications.md`, `style-guide.md`) apply to every screen; each file in `screens/` adds what is specific to that screen.
- **The files constantly reference each other** ("see `X.md`") rather than duplicating information. Follow these references rather than guessing: if a screen mentions a rule defined elsewhere (bilingual behavior, a color from the style guide...), the source of truth is the referenced file, not the screen citing it.
- **When modifying a spec**, look for the other files that reference it (`grep` the file name in `specs/`) and check that they remain consistent with the change. This is the most frequent source of inconsistency in this kind of project.
- **When in doubt, or when the specs are silent** on a point needed for the implementation, ask rather than assume: these are design choices, not free implementation details.
- **In case of contradiction** between the code (existing or being written) and a spec, the spec prevails; if the implementation reveals that a spec must change, update the spec and explain why, rather than silently diverging from it in the code.

## Before each commit

- **Check all the files in `specs/`** for consistency, not only those directly modified by the commit.
- **If one or more specs need adjusting** (to stay consistent with each other, or with the change in progress), block the commit: propose the necessary updates and wait for approval before applying them, then commit.

## Established conventions

- Everything in the repository is written in English: specs, this file, READMEs, code comments, script output, commit messages. The only exception is the site's published French content (French pages, French illustration files and concept data, French UI strings in the layouts), which stays in French.
- File and folder names, data attributes, CSS classes and technical identifiers are in English, in kebab-case (e.g. `illustration-card`, `ill-card-title`, `_illustrations/`). Exception: illustration slugs are French (e.g. `loi-brooks`), since they appear in the published URLs.
- The colors and components of the style guide are defined only once, in `style-guide.md`: do not introduce new color values or new component styles elsewhere without adding them there first.
- The site's style guide palette (chrome, sidebar, pages) and the palette of the SVG illustrations themselves (navy background, gold, generated by `generator/`) are two distinct color systems: see `style-guide.md`.
